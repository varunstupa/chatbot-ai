Architecture reference · chatbot-ai

Admin Chatbot Code Map

Which file does what in the admin-app assistant: where the APIs live, where configuration and the model are set, where guardrails are enforced, and how a question travels from the Angular widget to the LLM and back.

1. The big picture

The admin-app assistant answers "how do I…" questions about the screen the user is on. It is a RAG system: answers are generated by a local LLM, but only from passages of hand-written Markdown screen guides retrieved from a vector database. Three code bases take part:

Frontend · SaaS_Admin (Angular)

Chat widget on event screens. Sends the question, the login token and the current route.

API gateway (FastAPI)

Verifies the login JWT, signs tenant/user/role with HMAC, forwards to the chatbot under /chatbot/v1/*.

chatbot-ai (FastAPI)

Checks the signature, finds guides the tenant may read, retrieves passages, calls the LLM, streams the answer.

Ollama + Chroma

Ollama runs the LLM (llama3.2:3b). Chroma (embedded, on disk) stores guide chunks as vectors.

Two chat products share the chatbot-ai repo. This guide is about the admin-app chat (/app-chat). The older public Stupa website chat (/stupa-chat, /query, website crawler, demo booking) is still in app/api/routes.py and related services, but is a separate product. Tables below mark files as admin chat, Stupa chat or shared.

2. One question, end to end

sequenceDiagram
  participant W as Angular widget
  participant G as Gateway /chatbot/v1
  participant A as chatbot-ai /api/app-chat
  participant K as Registry + Chroma
  participant L as Ollama LLM
  W->>G: POST question, screen route, login JWT
  G->>G: auth_decorator verifies JWT
  G->>A: forward + X-Chat-Tenant/User/Role + HMAC signature
  A->>A: auth.require_scope checks signature, builds CallerScope
  A->>A: ticket_workflow.try_process - is this a report-an-issue turn
  A->>K: app_chat.retrieve: guides this tenant may read, current screen first
  K-->>A: passages + distances (filtered by thresholds)
  alt no passage close enough
    A-->>W: no_answer_message (LLM is not called)
  else passages found
    A->>L: system message + history + prompt(context, question, screen)
    L-->>A: tokens
    A-->>G: SSE stream - session, sources, tokens, done
    G-->>W: streamed back unbuffered
  end
  1. Widget (tournament-chatbot-widget.component.ts) collects the question; ChatScreenContextService adds the route pattern (e.g. tms/event-settings/create-event/:event_id) and URL; TournamentRagQueryService POSTs it with the auth header.
  2. Gateway (routers/chatbot_router.py) runs the existing @auth_decorator, then services/chatbot_service.py signs the verified identity and streams the request to chatbot-ai.
  3. chatbot-ai route app/api/app_chat.py → app_chat_query gets a CallerScope from app/services/auth.py → require_scope. The tenant never comes from the request body.
  4. If the message starts or continues the Jira ticket wizard, ticket_workflow.try_process answers instead of the LLM.
  5. app/services/app_chat.py → retrieve picks passages: a screen named in the question, else the current screen, else any visible guide, using distance thresholds from config.
  6. app/services/rag_pipeline.py → stream_answer skips the LLM when nothing was found, otherwise builds the prompt and streams from Ollama via LangChain, keeping per-session history.
  7. Every answer is audit-logged (app_chat.audit: tenant, user, route, mode, doc_ids).

6. Configuration

How settings are loaded

  1. app/config/settings.py → _default_config_path() chooses the YAML: CONFIG_FILE env var if set; config.production.yaml when APP_ENV=production (set in the Dockerfile and compose); otherwise config.yaml.
  2. YamlSettingsSource reads it; Settings (Pydantic) validates every section, e.g. AppChatConfig rejects a prompt without {context}, {question}, {screen}.
  3. Secrets come from environment / .env through validation_alias fields on Settings. They are never in YAML.
  4. get_settings() caches one instance; app/bootstrap.py can reload it.

9. Knowledge pipeline (guides → vectors)

  1. Write a guide in guides/<module>/<area>/<screen>.md with YAML front matter: doc_id, title, routes (Angular route pattern), aliases, tenants, exclude_tenants, roles, suggested_questions. Rules in guides/README.md.
  2. Load: on every start guide_loader.load_guides() reads all *.md (except README). Duplicate doc_id is an error.
  3. Parse: parser.parse_guide validates front matter; content_hash fingerprints title + body + chunker version.
  4. Skip or re-embed: service.ingest_guide skips unchanged content; access-only edits update only the registry.
  5. Chunk: parser.build_chunks splits on ## headings, keeps each FAQ **Question?** pair alone, prefixes "Title – Section" so the embedding knows the screen.
  6. Store: index.ChunkIndex.replace_document embeds and writes chunks to Chroma; registry.upsert makes the guide readable.
  7. Prune: guides whose file was deleted are removed, unless any guide failed to load (a typo cannot take others offline).

Retrieval order at question time (app_chat.retrieve)

  1. named: the question mentions another screen's title/alias → search that guide.
  2. screen: search the guide(s) of the current route (tenant overlays first).
  3. fallback: search all visible guides; another screen wins only if closer by other_screen_margin.
  4. overview: vague "how does this page work?" → opening chunks of the current guide.
  5. none: nothing relevant → no-answer message, LLM not called.

14. Known limits (be ready to say these)

Single worker. Chat history (chat_memory.py) and the Chroma store are per process; scaling out needs sticky sessions or Redis-backed history.

No dedicated prompt-injection or PII filter. Protection comes from grounding (no context → no LLM call, "answer only from Context"), strict tenant scoping of what the model can see, and temperature 0.

No rate limit on questions. Only attachment uploads are rate-limited; question volume is bounded by gateway auth.

Guides are written by hand from the Angular code; when a screen changes, its guide must be updated (workflow in guides/README.md).

Stale comment: the YAML comment "one Chroma collection per tenant" is outdated; there is one shared collection and the registry decides access.

15. Questions you may get, with short answers

How do you stop tenant A from seeing tenant B's content?
The tenant comes only from the gateway-signed identity (or verified JWT). The registry lists which tenants may read each guide; Chroma is queried only for those doc_ids, and every hit is checked again in _checked_hit. 68 tests cover this.
Why a gateway signature instead of passing the JWT?
The gateway already verifies the login token. Signing tenant/user/role with a shared secret means the chatbot needs no public key and cannot be called directly with a forged identity; the 60-second timestamp blocks replays.
How does it know which screen the user is on?
The widget sends the Angular route pattern; guides declare routes in front matter; guides_for_screen matches the pattern, or the URL as a fallback.
What happens for an unrelated question?
No passage passes the distance thresholds, so the LLM is not called and the user gets the configured no-answer message, which points to "report an issue".
Why a 3B model?
It runs on CPU within about 4 GB RAM, answers are grounded in short retrieved passages, and temperature 0 keeps them consistent. Swapping models is one YAML value plus OLLAMA_MODEL.
How are guides updated?
Edit the Markdown and restart (or redeploy). The loader re-embeds only changed guides by content hash and removes deleted ones.
Where would I add a new endpoint?
Admin chat: app/api/app_chat.py with Depends(require_scope); logic in app/services/; expose it through a new route in the gateway's chatbot_router.py.
How is a support ticket created?
Messages like "report an issue" are caught by ticket_workflow.try_process before RAG; the wizard collects fields and attachments, then jira_provider.create_ticket calls the Jira REST API.
